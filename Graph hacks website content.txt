01 / The challenge

Give your agent the context to act
Build a working agent, or a group of agents, with FalkorDB as its context layer. The graph has to shape what the agent does, not sit on the side.

The problem

Agents see pieces, not the whole picture. They lose track of what happened in earlier sessions, miss how people, systems, and records relate, and can't explain why they made a choice.

The shift

Put the agent's context in a graph. Data, memory, and company knowledge become nodes and edges the agent can follow, so it works from real relationships instead of guessing.

The brief

Build an agent that acts on connected data, remembers what it learns, and can show how it got to each answer.

Work the graph has to do

Follow connections across data
Remember across sessions
Share state between agents
Connect people, projects, and decisions
Show the path behind an answer
One agent problem
Pick a task where the answer depends on how things connect, and build the agent that handles it.

Solo or a team of four
Enter on your own or with up to three others. Register once, either way.

Open worldwide
Free to enter, online from anywhere, and no graph database experience needed.

Three tracks
Agents that act on connected data, agent memory and coordination, or company brain. Enter the one your idea fits.

02 / Tracks

Three tracks
Build for one, or for all three at once. Each track has its own prize.

🕵️
Track 01

Agents That Act on Connected Data
Build an agent that uses the graph to decide and act. It could investigate fraud, triage security findings, or work through a codebase.

Key focus

Multi-hop reasoning
Graph queries and algorithms as agent tools
Tool selection through MCP
Actions based on what the graph shows
Explainable results
🤖
Track 02

Agent Memory and Coordination
Build agents that remember across sessions and share state with each other. Memory should persist, update over time, and be available to every agent that needs it.

Key focus

Episodic, semantic, and procedural memory
Persistent conversation history
Shared state and handoffs between agents
High-concurrency reads and writes
Separate memory per user or tenant
🧠
Track 03

Company Brain
Build an agent that understands how a company works. Connect people, teams, projects, documents, and decisions in one graph, so the agent can answer questions and get work done across all of it.

Key focus

Knowledge from docs, tickets, and chats in one graph
Who owns what, and who knows what
Tracing decisions back to their source
Keeping knowledge current as things change
Answers with clear sources

03 / Why graphs

Agent questions are about connections
The hard questions agents get asked don't live in one record. The answer depends on how several things relate.

01
Which accounts are linked to this flagged transaction?

02
What did this customer ask for last month, and was it resolved?

03
Who on the team has worked on this system before?

04
What breaks if this service goes down?

A graph database stores those relationships directly, so the agent can follow them in one query instead of stitching records together on every step.

Rules

Everything you're held to
Read these before you start building. Registering for Graph Hacks means agreeing to all of them, along with the WeMakeDevs Code of Conduct.

1.
You can participate solo or in a team of up to 4 members. Each participant may only be part of one team.

2.
Required technology: FalkorDB must be the primary graph database in your project, and it must support a central part of what the product does.

3.
The graph has to do real work. A visualisation drawn on top of ordinary storage does not qualify: if the product still works once FalkorDB is taken out, the graph is decoration rather than the thing the product runs on.

4.
Run FalkorDB however suits you. Docker, a self-hosted instance, and FalkorDB Cloud are all accepted, and you may use any language, framework, frontend, or deployment platform alongside it.

5.
The challenge is open-ended within the three tracks: Agents That Act on Connected Data, Agent Memory and Coordination, and Company Brain. You may enter any or all of them, and you must name every track you are entering when you submit.

6.
Your project must use data you are allowed to use: public, synthetic, or your own. Do not load private, login-protected, paywalled, personal, or otherwise restricted information into your graph.

7.
The hackathon runs from October 15, 12:01 AM IST to October 18, 11:59 PM IST. Submissions close at the end of that window.

8.
The main coding and design work must begin after the hackathon starts. You may discuss ideas, create notes, sketch the graph model, or prepare diagrams beforehand.

9.
You may use frameworks, open-source libraries, public APIs, templates, third-party tools, and publicly available datasets and assets. The original work completed during the hackathon will be judged.

10.
Every submission must include:

A public source-code repository
A README with setup instructions and your graph data model
The Cypher queries or graph algorithms the product depends on
A demo video showing the working project
A live deployment, or complete local setup instructions if it cannot be deployed
The track you are entering
11.
AI coding assistants are allowed, but their use must be disclosed.

12.
Participants must understand the submitted code and be able to explain the graph model, the queries, the project architecture, and the technical decisions behind them.

13.
Projects that are entirely generated using AI without meaningful participant contribution, verification, or technical understanding may be rejected.

14.
The prize pool is worth $20,000. The best project in each track wins a prize: an iPhone 18 Pro for Agents That Act on Connected Data, a PS5 with GTA VI for Agent Memory and Coordination, and an M6 Mac Mini for Company Brain. Every member of a winning team gets the prize.

15.
Any intellectual property developed during the hackathon belongs to the participant or team that created it. Teams are encouraged to agree internally on ownership before submitting.

16.
Treat participants, organisers, sponsors, speakers, judges, and community members with respect.

17.
Harassment, discrimination, plagiarism, or attempts to manipulate the judging process will result in disqualification.

18.
Failure to follow these rules or the WeMakeDevs Code of Conduct may result in disqualification.

Note: Graph Hacks is an independent developer hackathon organised by WeMakeDevs in collaboration with FalkorDB. These rules, the schedule, and the prize breakdown may be updated before the hackathon begins, and any change is announced through the WeMakeDevs and FalkorDB community channels.

Rules

Everything you're held to
Read these before you start building. Registering for Graph Hacks means agreeing to all of them, along with the WeMakeDevs Code of Conduct.

1.
You can participate solo or in a team of up to 4 members. Each participant may only be part of one team.

2.
Required technology: FalkorDB must be the primary graph database in your project, and it must support a central part of what the product does.

3.
The graph has to do real work. A visualisation drawn on top of ordinary storage does not qualify: if the product still works once FalkorDB is taken out, the graph is decoration rather than the thing the product runs on.

4.
Run FalkorDB however suits you. Docker, a self-hosted instance, and FalkorDB Cloud are all accepted, and you may use any language, framework, frontend, or deployment platform alongside it.

5.
The challenge is open-ended within the three tracks: Agents That Act on Connected Data, Agent Memory and Coordination, and Company Brain. You may enter any or all of them, and you must name every track you are entering when you submit.

6.
Your project must use data you are allowed to use: public, synthetic, or your own. Do not load private, login-protected, paywalled, personal, or otherwise restricted information into your graph.

7.
The hackathon runs from October 15, 12:01 AM IST to October 18, 11:59 PM IST. Submissions close at the end of that window.

8.
The main coding and design work must begin after the hackathon starts. You may discuss ideas, create notes, sketch the graph model, or prepare diagrams beforehand.

9.
You may use frameworks, open-source libraries, public APIs, templates, third-party tools, and publicly available datasets and assets. The original work completed during the hackathon will be judged.

10.
Every submission must include:

A public source-code repository
A README with setup instructions and your graph data model
The Cypher queries or graph algorithms the product depends on
A demo video showing the working project
A live deployment, or complete local setup instructions if it cannot be deployed
The track you are entering
11.
AI coding assistants are allowed, but their use must be disclosed.

12.
Participants must understand the submitted code and be able to explain the graph model, the queries, the project architecture, and the technical decisions behind them.

13.
Projects that are entirely generated using AI without meaningful participant contribution, verification, or technical understanding may be rejected.

14.
The prize pool is worth $20,000. The best project in each track wins a prize: an iPhone 18 Pro for Agents That Act on Connected Data, a PS5 with GTA VI for Agent Memory and Coordination, and an M6 Mac Mini for Company Brain. Every member of a winning team gets the prize.

15.
Any intellectual property developed during the hackathon belongs to the participant or team that created it. Teams are encouraged to agree internally on ownership before submitting.

16.
Treat participants, organisers, sponsors, speakers, judges, and community members with respect.

17.
Harassment, discrimination, plagiarism, or attempts to manipulate the judging process will result in disqualification.

18.
Failure to follow these rules or the WeMakeDevs Code of Conduct may result in disqualification.

Note: Graph Hacks is an independent developer hackathon organised by WeMakeDevs in collaboration with FalkorDB. These rules, the schedule, and the prize breakdown may be updated before the hackathon begins, and any change is announced through the WeMakeDevs and FalkorDB community channels.

Give your agent the context to act
Build a working agent, or a group of agents, with FalkorDB as its context layer. The graph has to shape what the agent does, not sit on the side.

The problem

Agents see pieces, not the whole picture. They lose track of what happened in earlier sessions, miss how people, systems, and records relate, and can't explain why they made a choice.

The shift

Put the agent's context in a graph. Data, memory, and company knowledge become nodes and edges the agent can follow, so it works from real relationships instead of guessing.

03 / Why graphs

Agent questions are about connections
The hard questions agents get asked don't live in one record. The answer depends on how several things relate.

01
Which accounts are linked to this flagged transaction?

02
What did this customer ask for last month, and was it resolved?

03
Who on the team has worked on this system before?

04
What breaks if this service goes down?

A graph database stores those relationships directly, so the agent can follow them in one query instead of stitching records together on every step.

An open-source graph database built for AI agents.

Traversals are fast enough to run on every step of an agent loop, and one instance can hold thousands of isolated graphs, so each user, agent, or tenant gets its own. Run it locally with Docker.
